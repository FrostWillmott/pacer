# Архитектурный аудит: pacer

Дата: 2026-07-02. Объём: ~800 строк кода приложения (`app/`), ~380 строк тестов,
плюс seed-скрипт, notifier и инфраструктура. Аудит read-only, код не менялся.

## Вердикт (TL;DR)

Архитектура для проекта такого масштаба — **хорошая, местами образцовая**.
Слои разделены осознанно, чистая функция `compute_progress` как ядро домена —
сильное решение, `docs/DECISIONS.md` — редкий для pet-проекта уровень
документирования trade-off'ов, и он честный (решения реально соответствуют коду).
Выдуманных проблем здесь нет: репозиторный слой, Redis, Celery проекту не нужны,
и отказ от них обоснован письменно.

Реальные слабости не структурные, а **операционные**: единственный критичный
write-путь (ежедневный job) — одновременно наименее защищённое и наименее
протестированное место в кодовой базе. Плюс две точки, где код противоречит
собственной документации, — для портфолио-репозитория это заметнее, чем баг.

### Системные темы (проходят через весь проект)

1. **Надёжность daily_job недоинвестирована относительно его критичности.**
   Весь продукт — это один cron-запуск в день. При этом: ответ LeetCode не
   валидируется по форме (200 + `"data": null` уронит job необработанным
   `TypeError`), оркестрация `daily_job` не покрыта ни одним тестом, а сбой
   каскадом даёт *тишину* (job упал → digest пустой/вчерашний → notifier молчит,
   и «молчит из-за сбоя» неотличимо от «молчит, потому что нечего делать»).
2. **Документация чуть впереди кода.** Два места, где заявленные правила
   нарушены самим кодом (см. §5, пункты 1–2). Для репозитория, который
   демонстрирует дисциплину через `.claude/rules/` и DECISIONS.md, это дороже
   обычного.
3. **Корректность дат держится на неявной цепочке таймзон.**
   `.env TZ` → окружение контейнера Postgres → `initdb` → session `timezone`
   GUC → семантика `cast(next_review_at, Date)`. Каждое звено сейчас совпадает,
   но ни одно не закреплено явно и не проверено тестом (см. §2).

## 1. Архитектура и связность модулей

**Разделение слоёв — есть и соблюдается почти везде.**
`routers/digest.py` → `services/{digest,progress,sync}.py` → `db/{models,session}.py`.
Направление зависимостей одностороннее, циклических импортов нет (проверено по
импортам всех модулей). Репозиторного слоя нет намеренно — задокументировано в
CLAUDE.md, и для 3 таблиц это правильный выбор, а не упущение.

**Сильные места:**

- `services/progress.py` — чистое ядро домена: fold без I/O, без импорта
  Settings, конфиг передаётся аргументами. Это то самое место, где интервью
  превращается в разговор о design, а не об оправданиях.
- `sync.py` изолирован как хрупкая интеграция: весь LeetCode HTTP в одном файле,
  fetch отделён от reconcile, reconcile тестируется списком словарей без mock
  HTTP-клиента.
- Разделение «scheduler пишет / GET читает» проведено последовательно:
  `introduce_if_needed` недостижим из HTTP-слоя.
- God-объектов нет; самый большой модуль (`services/sync.py`, 185 строк) — это
  две функции с ясными зонами ответственности.

**Слабости:**

- **`/progress/summary` нарушает собственное правило слоёв.** В
  `app/routers/digest.py:50-81` роутер сам строит два SQLAlchemy-запроса с
  `group_by`, хотя `backend-fastapi.md` и README заявляют «routers — HTTP only».
  Digest идёт через сервис, summary — нет. Непоследовательность заметна именно
  потому, что во втором endpoint'e правило соблюдено.
- **`introduce_if_needed` живёт в `services/digest.py`, но к digest не
  относится** — это write-логика планировщика. Модуль фактически содержит два
  несвязанных use case (сборка digest и введение задач), объединённых по
  принципу «про задачи». Не критично при таком размере, но это первый кандидат
  на распад при росте.
- **Дублирование `_read_env`** в `notifier/notify.py:19-29` и
  `notifier/install_agent.py:30-40` — копипаста один-в-один. Мелочь, но ровно
  та, которую замечает ревьюер.
- **Engine создаётся на уровне модуля** (`app/db/session.py:9`): любой импорт
  модуля читает настройки и конструирует engine. Работает (соединения лениво),
  но лишает гибкости — тесты вынуждены строить собственный engine и подменять
  `get_db`, а engine приложения никогда не `dispose()`-ится при shutdown
  (lifespan в `main.py` его не закрывает).

## 2. Асинхронность и работа с БД

**В целом async SQLAlchemy 2.0 используется грамотно.** Всё через
`AsyncSession`, lazy loading нигде не срабатывает (в `_to_summary` читаются
только колонки `Problem`, relationships в запросах digest не трогаются — N+1
физически нет). Блокирующих вызовов в async-путях нет: `subprocess`/синхронный
`httpx` живут только в хостовых скриптах, работающих вне event loop.

**Транзакции.** `daily_job` оборачивает sync + introduce в одну транзакцию
(`session_factory() as session, session.begin()`) — атомарность правильная:
либо submissions + пересчёт progress + новая задача коммитятся вместе, либо
ничего. HTTP-запрос к LeetCode лексически находится *внутри* `session.begin()`,
но реального соединения с БД в этот момент ещё нет (SQLAlchemy берёт connection
на первом execute), так что транзакция не висит открытой 10 секунд таймаута —
однако форма кода подсказывает обратное, и это придётся объяснять.

**Находки, по убыванию серьёзности:**

- **`cast(next_review_at, Date)` зависит от таймзоны сессии БД, а не от
  `settings.tz`.** В PostgreSQL `timestamptz::date` конвертирует через GUC
  `timezone` соединения. `today` в роутере считается в `settings.tz`, а
  date-cast на стороне БД — в таймзоне, которую Postgres унаследовал от `TZ` в
  окружении контейнера при initdb. Сейчас обе — `Europe/Moscow` из одного
  `.env`, поэтому работает. Но если БД окажется в UTC (дефолт официального
  образа без `TZ`, managed Postgres, другой compose), ревью, решённое в 01:00
  по Москве, «уедет» на предыдущий день. DECISIONS.md подробно разбирает
  таймзону роутера и молчит про таймзону БД — слепое пятно ровно в том месте,
  которым проект гордится. Лечится либо `connect_args={"server_settings":
  {"timezone": settings.tz}}` в engine, либо заменой cast на сравнение с
  границей дня (`next_review_at < начало завтрашнего дня в local tz`) — второй
  вариант заодно возвращает индексу применимость.
- **Тот же `cast` делает индекс `ix_progress_next_review_at` бесполезным для
  фильтра** — функция над колонкой не даёт range scan. На 200 строках это ноль
  миллисекунд, но связка «создал индекс — завернул колонку в cast» — готовый
  вопрос на собеседовании.
- **`sync_submissions` грузит всю таблицу submissions в память** для дедупа
  (`app/services/sync.py:88-96`) — и все slugs problems, и все slugs progress.
  При масштабе проекта (сотни строк) это осознанно-нормально, но «почему не
  `WHERE problem_slug IN (...)` по батчу или `INSERT ... ON CONFLICT DO
  NOTHING`, раз constraint уже есть?» — вопрос, на который стоит иметь ответ
  лучше, чем «так проще».
- **Check-then-insert гонка в `introduce_if_needed`**: подсчёт introduced и
  вставка не защищены ни блокировкой, ни constraint'ом. Два конкурентных
  запуска job'а введут две задачи. При одном инстансе и одном cron в день —
  теоретическая, но БД-инвариант «introduced ≤ квота» нигде не закреплён.
- Пул соединений — дефолтный, без конфигурации. Для single-user корректно;
  просто знать, что `pool_size`/`pool_pre_ping` не настроены сознательно.

## 3. Обработка ошибок и edge cases

Redis и Celery в проекте отсутствуют (и правильно), поэтому анализ — про три
реальные внешние зависимости: LeetCode API, PostgreSQL, планировщик/хост.

**LeetCode (главный риск, что признано в коде):**

- `fetch_recent_ac` (`app/services/sync.py:51-69`) обрабатывает только
  HTTP-уровень (`raise_for_status` + `except httpx.HTTPError` в `daily_job`).
  **GraphQL-ошибки приходят как 200 с `{"errors": [...], "data": null}`** — в
  этом случае `data["data"]["recentAcSubmissionList"]` бросит `TypeError`,
  который `except httpx.HTTPError` не поймает, и job упадёт необработанным.
  То же с изменением формы полей (`raw["titleSlug"]`, `int(raw["timestamp"])`).
  Для модуля, чей docstring начинается со слова FRAGILE, отсутствие валидации
  формы ответа — главное несделанное дело.
- Ретраев нет — одна попытка в день. Смягчено дизайном: окно в 20 сабмитов
  означает, что завтрашний poll подберёт пропущенное. Но связка «job упал →
  введение новой задачи тоже пропущено» (ранний `return` в
  `app/scheduler.py:29-31` до `introduce_if_needed`) — недокументированное
  решение: падение LeetCode останавливает и ту часть системы, которая от
  LeetCode не зависит.

**Планировщик:**

- APScheduler 4.x (alpha, что честно закомментировано) с in-memory store.
  Комментарий в `main.py` объясняет, почему потеря расписания при рестарте не
  страшна. Но не разобран сценарий **«машина спит в 08:00»** — для локального
  macOS-деплоя это не edge case, а вторник. Что делает APScheduler с
  пропущенным cron-срабатыванием при проснувшемся контейнере (misfire), нигде
  не проверено и не сконфигурировано. launchd-агент notifier'а при этом missed
  events на wake обрабатывает — то есть уведомление может прийти по вчерашнему
  digest.

**Каскад тишины (систематическая тема №1):** notifier по дизайну молчит, когда
нечего делать, и *точно так же* молчит при любом сбое (`notify.py` печатает в
stderr → `/tmp/pacer-notifier.err`, куда никто не смотрит). Backend не имеет
`/health`, compose-сервис backend — без healthcheck. Итог: единственный
пользователь узнаёт о том, что система умерла неделю назад, только заметив,
что «давно не было задач». Для трекера привычек это худший failure mode —
отказ неотличим от успеха.

**БД:** миграция запускается на старте контейнера (`alembic upgrade head` в
CMD) после healthcheck'а Postgres — корректно. FK без `ondelete` означает, что
удаление problem с историей упадёт — приемлемо (удаления нет как операции).

## 4. Тесты

**Это настоящие тесты, не для галочки.** Признаки: доменное ядро покрыто
таблично по всем переходам состояний (`test_progress.py` — 7 тестов на fold,
включая идемпотентность); сервисы гоняются против реальной БД, mock — только
на границе HTTP (в полном соответствии с собственными правилами); CI двухэтапный
— SQLite для скорости + отдельный job против Postgres 16 для БД-специфичных
семантик, и различие между ними осмысленно прокомментировано прямо в ci.yml.
Имена тестов следуют конвенции `test_what_condition_expected`, ассерты
проверяют конкретные значения.

**Дыры в покрытии (по значимости):**

1. **`app/scheduler.py` — 0 тестов.** Оркестрация daily_job: транзакция,
   обработка сбоя fetch, порядок «sync → introduce» — самый критичный
   исполняемый путь проекта не покрыт вообще. Интеграционный тест «mock
   fetch_recent_ac → реальная сессия → job целиком» отсутствует.
2. **Флагманское поведение date-cast не тестируется напрямую.** DECISIONS.md
   посвящает date-cast два абзаца, но во всех тестах `next_review_at` лежит в
   прошлом на целые дни. Теста «ревью назначено на сегодня 14:00, digest
   запрошен в 08:00 — задача видна» нет, а это ровно тот случай, ради которого
   cast написан. И его Postgres-вариант заодно поймал бы проблему таймзоны БД
   из §2.
3. **Notifier — 0 тестов**, при том что в `notify.py:63-84` есть чистая
   логика форматирования (подсчёт, suffix «of N overdue»), тестируемая без
   единого mock'а.
4. Парсинг ответа `fetch_recent_ac` (`data["data"][...]`) не тестируется — та
   самая необработанная форма ответа из §3.
5. `make coverage` с порогом 70% существует, но в CI не вызывается — порог
   ничего не enforce'ит.

## 5. Что будет неудобно объяснять на собеседовании

1. **«У вас в docstring sync.py и в CLAUDE.md написано: no other module imports
   from this file. А `app/scheduler.py:14` импортирует из него две функции».**
   Имеется в виду «никто, кроме sync.py, не разговаривает с LeetCode», но
   написано другое, и написанное — ложно. Формулировку надо чинить.
2. **«Правила проекта: routers — HTTP only. Почему `/progress/summary` строит
   запросы прямо в роутере?»** (§1). Ответа «так исторически» у портфолио-репо
   быть не должно.
3. **«Переменная называется `NEW_PROBLEMS_PER_DAY_TOTAL`. Если я поставлю 3,
   я получу 3 новых задачи в день?»** Нет: код (`introduce_if_needed`)
   реализует cap «не больше N одновременно в статусе introduced» и вводит
   максимум одну задачу за вызов. Семантика «one in flight» задокументирована
   в DECISIONS.md и осмысленна, но имя переменной обещает per-day квоту,
   которой нет. Придётся объяснять расхождение имени и поведения.
4. **«Что произойдёт, если LeetCode вернёт 200 с GraphQL-ошибкой?»** —
   честный ответ сейчас: «job упадёт с TypeError, и я узнаю об этом никогда,
   потому что notifier молчит одинаково при сбое и при пустом дне» (§3).
5. **«Вы создали индекс по next_review_at и тут же завернули колонку в cast.
   Индекс используется? А в какой таймзоне Postgres кастует timestamptz к
   date?»** — двойной вопрос из §2; на первый ответ «нет, но строк 200», на
   второй сейчас внятного ответа нет.
6. **«Alpha-зависимость (APScheduler 4.0a5) в проде — почему?»** — ответ
   наполовину есть (закомментирован pin и причина), но добавить «и что будет
   при misfire, я проверил» пока нельзя.

Что объяснять **удобно** (и стоит проговаривать самому): чистый fold + progress
как кэш; отсутствие статуса `review`; `introduced_at NOT NULL` ради DESC-сортировки;
идемпотентный re-poll через UniqueConstraint + in-memory set; отказ от SM-2 из-за
отсутствия сигнала сложности. Это сильные, письменно обоснованные решения.

## 6. Топ-5 приоритетных изменений

1. **Валидация формы ответа LeetCode + обработка не-HTTP сбоев в daily_job.**
   *Маленький фикс* (десятки строк: проверить `errors`/`data is None`, обернуть
   парсинг, поднять доменное исключение, поймать его в `daily_job` рядом с
   `httpx.HTTPError`). Приоритет №1, потому что это единственный write-путь
   системы, его отказ сейчас частично не обрабатывается, а режим отказа —
   тихий. Всё остальное в проекте переживёт сутки простоя; это — источник
   простоя.
2. **Интеграционный тест `daily_job` + тест граничной семантики date-cast
   (в т.ч. в Postgres-job CI).** *Маленький/средний* (новый тестовый модуль,
   mock только `fetch_recent_ac`). Закрывает две крупнейшие дыры §4 разом и —
   главное — тест «ревью в 14:00 видно утром» против реального Postgres
   вскроет/зафиксирует таймзонную связку из п.3. Раньше п.3, потому что чинить
   таймзону без теста, который её ловит, — значит не знать, починил ли.
3. **Убрать зависимость date-cast от таймзоны сессии БД.** *Маленький фикс*:
   либо явный `server_settings={"timezone": settings.tz}` в
   `create_async_engine`, либо (лучше) заменить `cast(..., Date) <= today` на
   `next_review_at < <начало завтра в settings.tz>` — убирает скрытую связку,
   возвращает работоспособность индекса и снимает вопрос 5 из §5 целиком.
4. **Синхронизировать код с собственными правилами:** вынести запросы
   `/progress/summary` в сервис; переформулировать «no other module imports
   from sync.py» в docstring/CLAUDE.md/DECISIONS.md в то, что имелось в виду
   («вся коммуникация с LeetCode — только внутри sync.py; единственный
   потребитель — scheduler»). *Маленький фикс.* Приоритет выше «настоящих»
   фич, потому что репозиторий продаёт дисциплину, и два самопротиворечия
   обесценивают её быстрее, чем любой недостающий функционал.
5. **Переименовать `NEW_PROBLEMS_PER_DAY_TOTAL` под реальную семантику**
   (например, `MAX_NEW_IN_FLIGHT`) или изменить код до per-day семантики —
   первое правильнее, семантика «one in flight» осознанна. *Маленький фикс*
   (config + .env.example + README + DECISIONS). Последним в топе, потому что
   поведение корректно — лжёт только имя.

**За бортом топа (осознанно):** `/health` endpoint + healthcheck backend'а в
compose и «notifier уведомляет об ошибке, а не молчит» — следующий кандидат,
если чинить каскад тишины по-настоящему; проверка misfire-поведения APScheduler
при сне машины; `engine.dispose()` в lifespan; дедупликация `_read_env`.
Ничего из этого не вошло в топ-5, потому что каждый пункт либо меньше по
эффекту, либо (health/notifier) — прямое следствие пункта 1: пока daily_job
может падать молча, наблюдаемость — вторая половина той же задачи, а не
отдельная.

## Post-audit: что сделано (2026-07-02)

Все пункты топ-5 и большинство пунктов «за бортом топа» закрыты в этой же сессии.
Ключевое расхождение с исходным аудитом: причина молчания уведомлений оказалась
**не** в пунктах, которые предполагал аудит, а в самом планировщике.

**Реальная причина молчания (обнаружена, не предполагалась аудитом):** in-process
APScheduler `CronTrigger` внутри контейнера ни разу не сработал — Mac спал в
08:00 МСК (подтверждено `pmset -g log`: непрерывные Idle Sleep/DarkWake циклы всю
ночь). Контейнер жив, но wall-clock таймер в спящей VM не получает CPU-время.
Изначально это выглядело как баг APScheduler 4.0.0a6 (короткие интервалы
срабатывали, 10.5-часовой — нет) — гипотеза была неверной и скорректирована после
проверки `pmset`. **Не «уведомления работают неправильно» — `daily_job` вообще не
выполнялся, поэтому digest был пуст, и notifier молчал корректно.** Переписывание
на email ничего бы не исправило: канал уведомления — не источник проблемы.

Исправлено: `daily_job` теперь триггерится POST `/internal/daily-job` из
единого host launchd-агента (`notifier/notify.py`), который сам делает
trigger → wait → digest → notify последовательно — без гонки между двумя
агентами. См. `docs/DECISIONS.md` за полным обоснованием.

Также закрыто: валидация формы ответа LeetCode (§3.1), интеграционный тест
`daily_job` (§4.1), independence от таймзоны сессии БД в date-cast (§2, теперь
range-сравнение вместо `cast(...)`) + regression-тест на graniczный случай,
`/progress/summary` вынесен из роутера в сервис (§5.2), самопротиворечивые
docstring/README (§5.1), `NEW_PROBLEMS_PER_DAY_TOTAL` → `MAX_NEW_IN_FLIGHT`
(§5.3), `/health` + healthcheck backend'а в compose, notifier уведомляет о
сбое вместо молчания, дедупликация `_read_env`, `engine.dispose()` в lifespan.

Всё прогнано через `make check` (SQLite) и полный набор тестов против реального
Postgres (эфемерный контейнер, как в CI) — включая adversarial-проверку: тест
на date-cast boundary проходит даже когда сессия Postgres в UTC, а
`settings.tz` — Europe/Moscow (3 часа расхождения), что и должно было ловить
старый баг.

### Закрыто в тот же день: неинформативный баннер → terminal-notifier (2026-07-02)

Изначальная находка («текст баннера неразборчив») оказалась не багом прав
доступа, а недостатком самого формата: `display notification` через
`osascript` показывал только счётчик («1 new / 4 for review») без названий
задач и без возможности кликнуть и перейти к LeetCode. Пользователь запросил,
чтобы уведомление называло конкретные задачи со ссылками.

Решение: `osascript` заменён на [`terminal-notifier`](https://github.com/julienXX/terminal-notifier)
(`brew install terminal-notifier`, установлен и подтверждён пользователем
вживую). `notify.py` теперь формирует текст из реальных названий задач
(`New: ...`, `Review: ... (+N more overdue)`), клик по уведомлению открывает
фронтенд (`http://localhost:8000/`), где у каждой задачи есть ссылка на
LeetCode. `-group com.pacer.notifier` гарантирует, что повторные уведомления
заменяют предыдущее, а не копятся в Notification Center.

Найдена и исправлена реальная проблема окружения при внедрении: `launchd`
запускает агентов с минимальным `PATH`, не включающим `/opt/homebrew/bin` —
`shutil.which("terminal-notifier")` находил бинарник в интерактивном шелле,
но не под `launchd` (подтверждено через `launchctl kickstart`, где
`/tmp/pacer-notifier.err` показал ошибку "not found on PATH"). Исправлено
явным fallback на `/opt/homebrew/bin` и `/usr/local/bin`. После фикса
`launchctl kickstart` прошёл end-to-end без ошибок, пользователь подтвердил
читаемый баннер с кликабельной ссылкой. См. `docs/DECISIONS.md` за деталями.
